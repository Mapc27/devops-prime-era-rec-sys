# Рекомендательная система для маркетплейса: отчёт

**Сервис:** маркетплейс, рекомендации товаров. **Датасет:** Amazon Reviews 2023, Video Games (5-core).
**Код и запуск:** [README.md](README.md).

## 0. Контекст и данные

| Показатель | Значение | Что это значит для RecSys |
|---|---|---|
| Покупки / пользователи / товары | 814 тыс. / 94.7 тыс. / 24 тыс. | Небольшой, но реалистичный каталог |
| Плотность матрицы user × item | 0.034% | Сильная разреженность |
| Покупок на пользователя (медиана) | 6 | У трети пользователей ≤ 5 покупок, история короткая |

| Товаров с ≤ 10 покупками | 45% | Для половины каталога CF почти не работает |
| Покупки в тесте товаров, которых нет в train | **43%** | Холодный старт товаров важнее, чем пользователей |

Отзыв трактуется как покупка (implicit feedback). Валидация: глобальный сплит по времени,
последние 5% покупок (после 2022-08-05) идут в тест. Модель не видит будущего.
Тестовое окно длинное — 13 месяцев (до 2023-09-02) без переобучения модели: это занижает абсолютные метрики
и завышает долю новинок. Веса гибрида подбираются на отдельной валидации (последние 5% train), тест в подборе не участвует.

## 1. Часть I: реализованные подходы

| Группа | Подход | Блок на маркетплейсе |
|---|---|---|
| Бизнес-эвристики | Popular, Trending (популярность с затуханием 30 дней) | «Популярное», fallback |
| | AlsoBought (совместные покупки в окне 30 дней, штраф за популярность) | «С этим товаром покупают» |
| | SameBrand | «Другие товары бренда» |
| | История | «Недавно покупали» |
| Content-based | TF-IDF (название, бренд, категории, описание) + профиль пользователя | «Похожие товары» |
| Collaborative | User-based kNN, Item-based kNN, ALS (готовая библиотека `implicit`) | «Вам может понравиться» |
| Hybrid | Switching (нет истории → Trending) + смешивание рангов ALS + ItemKNN + Content + Trending (RRF) | «Вам может понравиться» |

### Результаты (K = 10, пользователи с историей)

| Модель | Recall@10 | NDCG@10 | HitRate@10 | Coverage | Novelty | TrendShare |
|---|---|---|---|---|---|---|
| Popular | 0.007 | 0.004 | 0.012 | 0.07% | 5.6 | 0% |
| Trending | 0.037 | 0.022 | 0.064 | 0.06% | 8.7 | 100% |
| AlsoBought | 0.009 | 0.006 | 0.018 | 37% | 10.5 | 2% |
| SameBrand | 0.011 | 0.006 | 0.019 | 16% | 8.0 | 3% |
| ContentBased | 0.012 | 0.007 | 0.022 | 56% | 12.3 | 1% |
| ItemKNN | 0.013 | 0.008 | 0.024 | 71% | 12.2 | 0% |
| UserKNN | 0.014 | 0.009 | 0.027 | 39% | 8.8 | 3% |
| ALS | 0.018 | 0.011 | 0.032 | 5% | 7.8 | 6% |
| Hybrid без Trending | 0.020 | 0.012 | 0.038 | 43% | 9.5 | 3% |
| **Hybrid** | **0.046** | **0.030** | **0.081** | 5% | 8.3 | 80% |

TrendShare — доля выдачи из топ-30 Trending: насколько «персональная» выдача совпадает с общей для всех.
Веса гибрида подобраны на валидации (последние 5% train, после 2021-07-26): ALS 1.0, ItemKNN 0.5, ContentBased 1.0,
Trending 2.0; без Trending — 1.0 / 1.0 / 1.0. Уже купленное исключается до отбора кандидатов каждой модели.

Новые пользователи: Popular NDCG@10 = 0.007, Trending = 0.023.

**Выводы:**
1. Простая эвристика (Trending) обходит каждую ML-модель по отдельности. В играх спрос сосредоточен вокруг свежих релизов.
   Любую модель надо сравнивать с сильным бейзлайном, а не с нулём.
2. Среди ML-моделей лучшая ALS, user-based лучше item-based по точности, item-based лучше по покрытию каталога.
3. Гибрид даёт +37% NDCG к Trending, но coverage падает с 43% до 5%: точность куплена ценой разнообразия.
4. Гибрид персонализирован слабо: 80% его выдачи — товары из топ-30 Trending. По сути это Trending,
   в который ML-модели подмешивают пару персональных позиций; прирост даёт в основном «свежесть».
5. Абсолютные значения низкие (HitRate 8%). Это нормально для каталога в 24 тыс. товаров при плотности 0.03%.
   Важно относительное сравнение.

## 2. Часть II-a: проблемы и ограничения подходов

### 2.1 Холодный старт пользователя (*все персональные модели*)
- **Проблема:** 12% тестовых покупателей новые. CF и content-based им ничего не дают.
- **Решение:** switching на Trending (реализовано), онбординг-опрос (любимые платформы и жанры),
  контекст (страница входа, рекламная кампания, гео, устройство), быстрая адаптация по первым кликам в сессии.
- **Проблема решения:** Trending не персонален. Опрос добавляет шаг и увеличивает отток на старте.
- **Обсуждение:** best practice — не заставлять, а предлагать: опрос в 1–2 клика с кнопкой «пропустить»,
  выдача по популярности с учётом контекста и сессионные модели, которые персонализируют уже после 2–3 действий.

### 2.2 Холодный старт товара (*CF: ItemKNN, UserKNN, ALS, AlsoBought*)
- **Проблема:** 43% покупок тестового периода — товары, которых не было в обучении (новые релизы).
  CF их не видит вообще. Офлайн-оценка такие покупки отфильтровывает и тем самым завышает реальное качество.
- **Решение:** content-based по атрибутам (реализован: похожесть по описанию, история покупок товара не нужна;
  в MVP каталог ограничен товарами с покупками, но для нового товара достаточно векторизовать его карточку),
  гибридные модели с признаками товаров (LightFM, two-tower),
  квота показов для новинок (exploration, многорукие бандиты).
- **Проблема решения:** у 27% товаров нет описания (ни описания, ни характеристик — у 6%), для них остаются название и бренд.
  Квота новинок отнимает показы у проверенных хитов, а значит и краткосрочную выручку.
- **Обсуждение:** стандарт — двухстадийная схема: кандидаты из нескольких источников, включая content и новинки,
  затем ранжирование. Отдельно — контроль качества карточек товара у продавцов (без описания хуже ранжируется).

### 2.3 Разреженность данных (*CF*)
- **Проблема:** плотность 0.034%, у трети пользователей ≤ 5 покупок, у 45% товаров ≤ 10 покупок. Оценки близости шумные.
- **Решение:** добавить более частые сигналы (просмотры, добавления в корзину, избранное) с разными весами;
  факторизация (ALS) вместо прямых kNN-соседей.
- **Проблема решения:** неявные сигналы шумные: просмотр ≠ интерес, случайный клик ≠ намерение купить.
- **Обсуждение:** веса по типу события (покупка > корзина > просмотр), учёт времени просмотра, фильтр ботов.

### 2.4 Popularity bias и длинный хвост (*Popular, Trending, ALS, Hybrid*)
- **Проблема:** 70% покупок приходится на 20% товаров. Модели воспроизводят и усиливают это:
  Trending покрывает 0.06% каталога, гибрид — 5%, и 80% его выдачи — товары из топ-30 Trending.
  Пример из API: покупателю игр для Wii и Xbox 360 гибрид рекомендует геймпад PS5, Zelda и стекло для Switch —
  9 из 10 позиций совпадают с Trending. Для маркетплейса это ещё и проблема продавцов:
  малые продавцы не получают показов.
- **Решение:** штраф за популярность, переранжирование на разнообразие (MMR, квоты по категориям и продавцам),
  фильтры по контексту (платформа пользователя).
- **Проблема решения:** офлайн-точность падает: наш гибрид без Trending разнообразнее (coverage 43%, TrendShare 3%), но NDCG на 59% ниже.
- **Обсуждение:** баланс задаётся бизнес-целью. Обычная практика — отслеживать coverage, novelty и долю
  длинного хвоста рядом с точностью и решать A/B-тестом. Офлайн-метрики систематически переоценивают популярное.

### 2.5 Пузырь фильтров и переспециализация (*Content-based, SameBrand*)
- **Проблема:** купил Tomb Raider — получаешь пять изданий Tomb Raider. Мало неожиданных находок.
- **Решение:** подмешивать рекомендации CF или исследовательские слоты, дедуплицировать издания одного тайтла.
- **Проблема решения:** часть исследовательских рекомендаций будет нерелевантна.
- **Обсуждение:** разделять блоки по назначению («Похожие» и «Вам может понравиться») и ограничивать долю одного бренда или серии в выдаче.

### 2.6 Взаимозаменяемые и уже купленные товары (*все модели*)
- **Проблема:** купил консоль — система предлагает ещё консоли (то же для геймпадов, карт памяти).
  Повторные покупки товаров длительного пользования маловероятны, а повторные покупки расходников нормальны.
- **Решение:** фильтр уже купленного (реализован), правила «после покупки X предлагать комплементарные товары»
  (AlsoBought частично это делает), разметка категорий: длительного пользования или расходник.
- **Проблема решения:** нужна ручная или полуавтоматическая разметка, правила устаревают.
- **Обсуждение:** различать «замены» (похожие) и «дополнения» (с этим покупают), использовать каждый тип на своей странице.

### 2.7 Неявный фидбек без негатива (*все модели*)
- **Проблема:** 11% «покупок» оценены на 1–2 звезды, но модель считает их положительным сигналом.
  Отсутствие покупки тоже не означает «не нравится».
- **Решение:** веса по рейтингу или возвратам, исключение возвратов, отдельный учёт «скрыть рекомендацию».
- **Проблема решения:** явных оценок мало, они смещены (пишут в основном очень довольные или очень недовольные).
- **Обсуждение:** использовать возвраты и кнопку «не интересно» как явный негатив, остальное оставлять implicit.

### 2.8 Сезонность и дрейф (*все модели, особенно ALS и kNN*)
- **Проблема:** пик в декабре–январе, спрос смещается к новым релизам. Модель, обученная месяц назад, устаревает.
- **Решение:** затухание по времени (Trending), регулярное переобучение, признаки сезона в ранжировщике.
- **Проблема решения:** частое переобучение стоит денег и рискует выкатить сломанную модель.
- **Обсуждение:** переобучать по расписанию с проверкой качества перед выкаткой, свежие сигналы подмешивать онлайн.

### 2.9 Масштабируемость (*UserKNN, Content-based*)
- **Проблема:** UserKNN на каждый запрос сравнивает пользователя со всеми остальными (~0.7 мс на пользователя на 95 тыс. пользователей,
  а на миллионах это секунды). Content-based считает близость ко всему каталогу.
- **Решение:** ItemKNN или ALS (матрица похожих товаров считается заранее), приближённый поиск соседей (FAISS, HNSW), предрасчёт.
- **Проблема решения:** приближённый поиск теряет часть точности, а предрасчёт устаревает.
- **Обсуждение:** user-based в индустрии почти не используют в чистом виде. Стандарт — item-to-item (Amazon, 2003) и эмбеддинги + ANN.

### 2.10 Этические проблемы (*AlsoBought, «люди также покупают»*)
- **Проблема:** без фильтрации «с этим покупают» и персональная выдача показывают неуместные связи.
  Примеры: Amazon в 2017 году предлагал вместе покупать компоненты для взрывчатки (расследование Channel 4).
  Target по покупкам вычислил беременность подростка раньше её семьи (NYT, 2012).
  В нашем каталоге — игры с рейтингом Mature, которые могут попасть детскому аккаунту.
  Также лутбоксы и внутриигровая валюта (близко к азартным играм) и продвижение собственных товаров площадки в ущерб продавцам.
- **Решение:** список чувствительных категорий и запрещённых связок, фильтр по возрастному рейтингу и возрасту аккаунта,
  запрет выводов о чувствительных характеристиках (здоровье, беременность, ориентация), аудит выдачи, прозрачность («почему мне это показали»).
- **Проблема решения:** ручные списки всегда неполны, фильтры режут и легитимные рекомендации, аудит дорогой.
- **Обсуждение:** правила + выборочная ручная проверка + жалобы пользователей как сигнал.
  Для маркетплейса это ещё и регуляторика: защита персональных данных (152-ФЗ / GDPR), антимонопольные требования к self-preferencing, DSA в ЕС.

### 2.11 Уязвимости: манипуляции и утечки (*CF, AlsoBought*)
- **Проблема:**
  1. *Shilling / data poisoning.* Наш датасет — отзывы, а накрутка отзывов — известная проблема маркетплейсов.
     Продавец с сотней фейковых аккаунтов, покупающих его товар вместе с хитом, попадает в «с этим покупают» хита.
     AlsoBought требует всего 2 совместные покупки (`min_support=2`), такая атака дешёвая.
  2. *Утечка приватности.* По изменениям публичных списков «с этим покупают» можно восстановить покупки
     конкретного человека (Calandrino et al., «You Might Also Like», 2011).
- **Решение:** учитывать только верифицированные покупки, антифрод (новые аккаунты, аномальные всплески),
  ограничить вклад одного пользователя, повысить порог поддержки, добавить шум или задержку в публичные блоки.
- **Проблема решения:** антифрод даёт ложные срабатывания, высокий порог ухудшает холодный старт, шум снижает точность.
- **Обсуждение:** вклад каждого аккаунта взвешивать по «доверию», мониторить резкие изменения в топах, обновлять публичные блоки батчами.

## 3. Часть II-b: проблемы в продакшене

| Проблема | Решение | Проблема решения | Обсуждение / best practice |
|---|---|---|---|
| **Медленный ответ.** Гибрид считает 4 модели по всему каталогу (~1 мс/пользователь здесь, на миллионах товаров — сотни мс) | Предрасчёт рекомендаций офлайн → кэш (Redis), ANN-индекс для эмбеддингов | Выдача не учитывает действия в текущей сессии | Гибрид: офлайн-кандидаты + лёгкое онлайн-ранжирование. Бюджет латентности p99 < 100 мс |
| **Падение сервиса рекомендаций** | Fallback на Trending (реализовано для новых пользователей), таймауты, circuit breaker | Fallback неперсонален, просадка конверсии незаметна без мониторинга | Пустой блок хуже популярного. Отслеживать долю fallback-ответов |
| **Устаревание модели** | Переобучение по расписанию (ALS у нас 10 с, на реальном каталоге — часы) | Стоимость, риск выкатить сломанную модель | Проверка метрик перед выкаткой, shadow/canary-релиз, быстрый откат |
| **Рекомендация отсутствующих товаров** | Постфильтр по остаткам и статусу карточки в реальном времени | Если фильтр вычеркнул много, выдача короткая | Брать с запасом (top-50 → фильтр → top-10) |
| **Расхождение признаков при обучении и в проде** (training/serving skew) | Общий код признаков, feature store | Сложность инфраструктуры | Логировать признаки, с которыми был сделан прогноз, и обучаться на них |
| **Петля обратной связи и position bias.** Модель учится на кликах по собственным рекомендациям | Логировать позицию показа, 1–5% трафика со случайной/exploration-выдачей | Exploration-трафик зарабатывает меньше | Без него модель всё сильнее сужает каталог (см. popularity bias) |
| **Расхождение офлайн- и онлайн-метрик** | A/B-тест каждого изменения | Нужен трафик и время (2–4 недели) | Офлайн — фильтр для кандидатов в A/B, решение — только по онлайну |
| **Качество данных** (дубли, боты, сломанный ETL) | Валидация данных на входе пайплайна, фильтр ботов | Ложные срабатывания проверок | Алерт при резком изменении объёма или распределения событий |
| **Масштабирование** (миллионы пользователей и товаров) | Item-based / эмбеддинги вместо user-based, шардирование, батч-инференс | Стоимость инфраструктуры | Считать стоимость рекомендации против прироста выручки |

## 4. Часть III: оценка работы в продакшене

### 4.1 Уровни метрик

| Уровень | Метрики | Когда и как |
|---|---|---|
| **Офлайн ML** | Precision/Recall/NDCG/MAP/HitRate@K, Coverage, Novelty, Diversity | Перед выкаткой, на сплите по времени. Порог: не хуже текущей модели |
| **Онлайн-поведение** | CTR блока, add-to-cart rate, конверсия в покупку из блока | Ежедневно, в разрезе блоков и сегментов (новые/старые) |
| **Бизнес** | Выручка (GMV) на пользователя, средний чек, число товаров в заказе, retention, доля продаж длинного хвоста и малых продавцов | A/B-тест, сравнение с контрольной группой (Trending) |
| **Guardrail** | Возвраты, жалобы, «скрыть рекомендацию», скорость загрузки страницы, нарушения политики (18+ детям) | Тест останавливают, если ухудшились, даже при росте выручки |
| **Системные** | Латентность p50/p95/p99, RPS, ошибки, **доля fallback-ответов**, попадание в кэш | Онлайн, алерты |
| **Здоровье модели и данных** | Возраст модели, свежесть данных, объём событий, дрейф распределений, coverage и доля топ-100 в выдаче | Ежедневно, алерт на скачки |

### 4.2 Как измерять эффект
- **Только A/B-тест** против бейзлайна. Контроль — Trending, а не «без рекомендаций»:
  иначе мы измеряем ценность блока, а не модели.
- **Главная метрика — инкрементальная выручка на пользователя**, а не «доля выручки через рекомендации».
  Многие клики по рекомендациям — покупки, которые произошли бы и так (каннибализация поиска и каталога).
- Длительность от 2 недель (недельная сезонность), учёт эффекта новизны.
- Отдельный разрез по новым пользователям: холодный старт улучшается или нет.

### 4.3 Что бизнес ожидает и что получит на самом деле

| Ожидание | Реальность |
|---|---|
| «+35% выручки, как у Amazon» | Цифра 35% — давняя оценка McKinsey, не результат A/B. В исследованиях (Jannach & Jugovac, 2019) реальный инкрементальный эффект обычно в единицах процентов |
| «ML сразу лучше текущей выдачи» | В нашем эксперименте каждая ML-модель по отдельности хуже Trending. Выигрыш дал только гибрид с эвристикой (+37% NDCG офлайн), и 80% его выдачи — те же хиты |
| «Персонализация для всех» | 12% тестовых пользователей без истории, 43% покупок — новинки, которых модель не видела. Для них работает content-based и популярное |
| «Офлайн +37% = онлайн +37%» | Офлайн-прирост обычно не переносится один к одному, бывает и обратный знак. Нужен A/B |
| «Внедрили и забыли» | Нужны переобучение, мониторинг, фильтры, разбор жалоб: постоянная стоимость команды и инфраструктуры |
| «Рост продаж хитов» | Рекомендации усиливают хиты. Если цель — продажи длинного хвоста и малых продавцов, это надо явно закладывать в выдачу |

Реалистичный результат для MVP: заметный прирост CTR и конверсии блоков по сравнению со случайным или просто популярным,
единицы процентов к выручке на пользователя. Основная ценность — в блоках «с этим покупают» и «похожие» на карточке товара,
где они увеличивают чек.

## 5. Как улучшить модель

1. **Валидация ближе к проду:** скользящее окно (обучение → неделя теста → дообучение) вместо одного теста длиной 13 месяцев.
2. **Новинки:** включить в оценку покупки новых товаров. Добавить в гибрид content-based кандидатов среди свежих товаров.
3. **Двухстадийная схема:** кандидаты (ALS, ItemKNN, content, AlsoBought, Trending) → ранжировщик на градиентном бустинге (CatBoost)
   с признаками пользователя, товара, цены, платформы и сезона.
4. **Контекстная популярность:** Trending по платформе пользователя (PS / Xbox / Switch / PC) вместо глобального. Ожидаемо снижает проблему «Zelda владельцу PS4».
5. **Разнообразие:** MMR-переранжирование, лимит на бренд или серию в выдаче, дедупликация изданий одного тайтла.
6. **Больше сигналов:** просмотры, корзина, возвраты, «не интересно» в качестве негатива.
7. **Эмбеддинги текста** (sentence-transformers) вместо TF-IDF для похожих товаров, а для 27% товаров без описания — изображения.
